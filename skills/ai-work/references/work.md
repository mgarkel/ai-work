# Step 3: The work

If the planning was thorough, the work should be straightforward. If you find yourself struggling, the plan may need another look.

## Start from the plan

- Read the whole `plan.md` and the sources it names. Don't repeat research the plan already did.
- If a source the plan names is missing or can't be opened, say so plainly. Don't quietly use something else.
- Read [kinds-of-work.md](kinds-of-work.md) and the user's rules for this kind of work.

## Do the work

- **Split the plan's steps into tasks** and order them by what depends on what.
- **Parts that truly stand alone** (three separate emails, a summary and a data pull) can be done at the same time by separate helpers if you have them. A single document is written in one go, so it reads in one voice. When unsure, do things one at a time.
- **Check in only at the plan's milestones.** A quick job has no check-ins; keep going to the end. Don't stop for approval after every task. At a milestone, show what's done in a few lines and what's next, and continue unless the plan says to wait.
- **Stop points are hard stops.** At each stop point in the plan, stop and wait for the user's approval.
- **Produce the real thing,** not a description of it. Save finished work where the project keeps it (see [files.md](files.md)).

## Check yourself as you go

- **A source for every fact.** Each fact, number, or quote in the output names where it came from (a file, a page, an email, a person). Anything without a source is labeled as an assumption or an estimate.
- **Recheck every number** against its source, and redo any calculation.
- **Use what's on the computer to check, not to build.** Counting words, adding up timings, or previewing a page is fine if it only reads and needs no install or permission prompt (see the hard stops in [SKILL.md](../SKILL.md)). Note in the log what you checked and how. If a check doesn't work, don't keep trying: put it on the user's list.
- **Go through the outcomes, the definition of done, and the checklist** line by line before calling a part finished.
- **At each step, ask yourself:** does this still serve the goal, the audience, and the constraints? Would the user be surprised by anything here? If yes, fix it or flag it.

## When something goes wrong

- **Missing information:** ask the user a specific question ("Which quarter's numbers should the update use, Q3 actuals or the forecast?").
- **Missing access:** note it in the log and carry on with tasks that don't need it.
- **The job is growing:** "This is turning into its own job. Should we give it a separate plan?"
- **Doubts about quality:** say so plainly ("I've drafted this, but I'm not confident about X because Y").

## Changes to the plan

- Small changes (wording, order, a better source): make them and record them in the running log with the reason.
- **Any change to the north star, the scope, or a stop point: stop and ask.**

## The running log

At each milestone, add to the "Running log" in `plan.md`: the date, what was produced and where, what changed from the plan and why, and anything blocked. Write it to the file, not just the chat; the debrief learns from it.

## Wrap-up

When the work is done (or everything left is blocked), give a short wrap-up:

- The deliverables and where they're saved.
- Decisions you made during the work, and why.
- Changes from the plan.
- Anything still open.
- **Confidence check:** what you're confident about and why (name the sources); what you're less confident about and what could go wrong; and your recommendation: proceed, proceed with a caveat, or pause for something specific. If everything is solid, two sentences is enough.

Add the wrap-up to the running log, set the job's status to `in review`, and go straight into step 4. The user can say "hold on" before the review starts.
